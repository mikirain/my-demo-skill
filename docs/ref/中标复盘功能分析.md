## 一、功能定位：补齐"投标后"这半条闭环

BidScope v1.0 是**投标前（ex-ante）**的竞品分析工作台：输入对手标书，输出差距与应答建议，评标结束即归档。中标复盘功能（PRD v1.1 增量）补齐的是**投标后（ex-post）**半条闭环——

> v1.0 解决「这一标怎么打」，中标复盘解决「下一标凭什么打得更好」。

它把一次中标从"一句口头结论"拆成三样可核对的东西：

1. **证据分级的赢因**：区分「已证实 A / 可能 B / 待验证 C」，强制区分"有直接证据"与"只有结果"；
2. **评分的机械对照**：评分因素表摊开「类别—因素—等级—证据条数—确认人」，让评审会能追问"这条 8 分是哪一页"；
3. **承诺的兑现状态**：履约验证逐条核对「承诺/目标/实际/偏差/状态」，把"赢过"和"做得到"分开看。

核心立场：**中标 ≠ 标书里每一项设计都导致了中标**。复盘的产出不是一次性报告，而是四类可检索、可复用的数据资产（经验库），报告只是经验库的视图。

## 二、解决的三个结构性缺失

v1.0 的三个缺口，正好对应本功能的三个核心机制：

| v1.0 缺失 | 对应机制 | 落点 |
| --- | --- | --- |
| 没有中标后的复盘对象（`BidResult` 只是枚举字段） | `AwardedProject` + `WinFactor`（评分因素）实体 | 中标复盘页 |
| 没有证据强度概念（所有结论平权） | A/B/C 证据分级 + BR 硬规则 | 三栏证据区 |
| 没有复用路径（情报库只存参数不存适用条件） | `Experience` 12 必填字段（含 `scope` 适用范围）+ 相似项目匹配 | 经验库 + `/match` |

## 三、核心机制分析

### 3.1 A/B/C 证据分级（本功能最重要的机制）

| 级别 | 定义 | 典型证据 | 可用于决策 |
| --- | --- | --- | --- |
| A 已证实 | 有直接证据 | 评分表得分、客户澄清邮件明确认可、评标反馈点名 | 可直接写入策略建议 |
| B 多材料 | 多项材料共同支持，无评标直接证据 | 投标文件 + 澄清记录 + 谈判记录共同指向 | 可作参照，需注明限制 |
| C 待验证 | 只有结果，无因果证据 | — | 只能标假设，禁止作为结论 |

支撑它的是 5 条硬规则（BR-11~15）：无来源不入库、C 级不进结论载体、无评分表最高 B 级、履约 missed 自动降级、引用留痕。**机制分析结论：分级本身不是难点，难点在"证据的物理可得性"**——A 级完全依赖正式评分表/评标反馈，而海外项目中评标反馈的获取率天然偏低（这正是 BR-13 存在的原因：它承认了大量项目只能复盘到 B 级的现实）。

### 3.2 经验条目：12 必填字段 + 四类经验库

四类库（竞品策略 / 技术响应与偏差 / 商务与交付 / 中标项目知识）对应 `competitor / deviation / commercial / awarded`。每条经验强制 12 字段（国家、规模、客户类型、投标模式、产品型号、招标要求、策略、结果、证据来源、复盘人、复核日期、**适用范围**），缺任一不可入库。

**关键设计**：`scope`（适用范围）字段使经验"可适配而非可照搬"——这是区分本功能与普通知识库的分水岭。配合相似项目匹配公式（国家 30 + 规模 25 + 技术路线 15 + 客户类型 15 + 合同模式 15），输出强制包含"可借鉴点"与"差异条件"两个区域，且匹配度只作排序依据。

### 3.3 履约验证与等级变更闭环（v1.1.1 增补）

- 履约四态 `met / partial / missed / pending`，`missed` 触发 BR-14 降级流程，必须填 ≥6 字复核说明（LR-03/LR-07）；
- 等级变更做成"可申请、可审批、可追溯"的流程（LR-01~08）：升级必须新增证据、升 A 必须有评分表、**双人规则（不可审批本人发起的变更）**、单条经验同时只允许一个待审变更；
- 这形成了经验的**生命周期管理**：`draft → verified → (deprecated)`，并可通过履约反馈持续修正投标期判断——这是"经验闭环"能自我纠错的关键。

### 3.4 人机边界（全功能的底线约定）

| AI/系统只能做 | 必须由人做 |
| --- | --- |
| 产出**建议**等级（标注"待人工确认"） | 证据等级最终确认 |
| 生成经验草稿（`draft` 态） | 入库审核（`draft → verified`）、`deprecated` |
| 机械执行 BR 规则拦截（脚本可保证） | 履约数据录入与季度核验 |
| 匹配度计算与可借鉴/差异条件解释 | 引用经验到新项目的确认与留痕 |

页面层面有配套约束：不产出报价、不产出承诺、不自动定级；C 级卡片不渲染任何"写入结论"类入口（用 UI 结构而非提示语来兜底 BR-12）。

## 四、用户角色与权限设计

8 个角色分三档（详见页面 PRD §2）：

- **编辑**：技术投标工程师（可改 B/C、发起变更、不可审批）、投标经理（全权 + 审批）、知识库管理员（可审批、不可删复盘）；
- **只读**：商务/报价（主视区为方案与商务）、法务/合规（默认落履约验证，"看得见风险但改不了等级"）、管理层（默认落经验三栏，导出默认脱敏）、观察者；
- **不可见**：系统管理员（直链也只见权限不足页，不泄露项目名）。

设计上值得肯定的两点：只读角色**不渲染**写入控件而非置灰（避免"看得见却点不动"的歧义）；等级用**形状编码**（A 实线 / B 双线 / C 虚线）而非仅颜色（无障碍 + 打印场景）。

## 五、实现现状分析（Skill 化视角）

### 5.1 适配性：★★★★★（系统内最适合 Skill 化的功能域）

理由：输入是非结构化多文档（招标要求、投标版本、评标反馈、澄清记录、履约数据），需要交叉印证与语义推理；输出是结构化判断（三栏证据 + 经验条目）；规则可脚本化（BR 校验、12 字段拦截、匹配打分）；天然有"初稿 + 人工确认"的审核兜底。

### 5.2 现有两个 Skill 对照

| 维度 | `bid-retrospective` | `bidscope-retro` |
| --- | --- | --- |
| 定位 | 通用中标复盘（十维度 + 模拟数据驱动报告） | BidScope F8 对齐版（评分因素/方案配置/商务/履约 + 经验入库） |
| 资源 | 3 references + generate_report.py + 8 个模拟数据 JSON + 报告模板 | 3 references + validate_experience.py + 报告模板 |
| 特色 | 模拟数据先行（结构即数据收集清单），数据校验 + 报告骨架脚本 | BR/LR 规则最完整，经验条目校验脚本可做字段级报错 |
| 验证状态 | 2026-10-25 补齐缺失资源后端到端跑通（曾因 SKILL.md 引用不存在的脚本/数据而不可执行） | 校验脚本正/负向路径均实测通过，已打包 dist |

**现存问题：两个 Skill 触发词高度重叠**（"中标复盘/投标复盘/复盘报告"），同时安装会导致 Agent 加载混乱。建议二选一：合并为一个（以 bidscope-retro 的规则体系为主干，吸收 bid-retrospective 的模拟数据与报告生成脚本），或明确切分（通用复盘 vs BidScope 产品内 F8 流程）。

### 5.3 Skill 与应用代码的边界

Skill 负责：十方面复盘推理、证据分级建议、经验条目草稿生成、报告骨架生成、BR 规则拦截校验。
应用代码负责：权限/审核流状态机、审计留痕、原文定位 UI、履约数据管理、经验库 CRUD——这些"必须机械保证"的部分不能交给 LLM。

## 六、风险与挑战

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| R1 | **证据可得性**：海外项目评标反馈获取率低 | A 级经验稀疏，经验库长期以 B 级为主，决策参考价值打折 | BR-13 已诚实处理（最高 B）；应增加"无评分表项目的替代证据"指引（客户感谢函、二次邀标事实），并统计各库 A/B/C 分布作为健康度指标 |
| R2 | **复盘执行率**：成功标准 S-01 要求中标后 2 周完成，实际常被交付压力挤掉 | 经验库无增量，功能空转 | 工作台待办卡（T-3 天提醒）已设计；建议把复盘完成率纳入投标经理考核，且复盘材料收集前置到投标结束即启动 |
| R3 | **C 级膨胀或 A 级通胀**：C 级条目堆积无人验证；或人为拔高等级 | 待验证区变"垃圾抽屉"；或错误经验被当结论复用 | C 级条目应有验证计划字段与到期复核；LR-01~08 审批流已防 A 级通胀，关键是审批人不能缺位 |
| R4 | **双 Skill 触发冲突** | Agent 加载混乱，产出口径不一 | 合并或切分（见 §5.2） |
| R5 | **履约数据滞后**：履约验证按季度核验，missed 反馈周期长 | 经验降级滞后，错误 A 级经验可能被引用多次 | BR-15 引用留痕可回溯受影响引用；建议 missed 确认后主动通知引用过该经验的项目 |
| R6 | **经验照搬**：用户只看匹配度排名不看差异条件 | 相邻期项目条件相似≠可复制 | 界面已强制"可借鉴 + 差异条件"双区呈现、匹配度标注"不代表可套用"；培训与场景演示要跟上 |

## 七、优化建议（按优先级）

1. **合并两个复盘 Skill**（高）：消除触发冲突，产物为一个 `bid-retrospective`：规则体系取 bidscope-retro（BR/LR 全量 + 字段级校验脚本），模拟数据与报告生成器取 bid-retrospective，重新打包并做端到端回归。
2. **给 C 级经验加"验证计划"**（高）：入库时必填"在哪个项目/什么时间验证"，到期未验证自动提醒复盘人——把 BR-12 从"禁止"升级为"有出口的暂存"。
3. **经验库健康度看板**（中）：统计 A/B/C 分布、入库量、引用次数、missed 降级数、C 级验证完成率，让"知识资产是否在增殖"可度量。
4. **无评分表项目的替代证据指引**（中）：在复盘 Skill 的 references 中明确 B 级证据的组合标准（如"客户澄清邮件 + 中标公示"可构成 B），减少等级判定的主观摇摆。
5. **复盘材料清单前置**（中）：投标结项时即生成"复盘材料收集清单"（评标反馈索取、澄清记录归档、谈判纪要归档），避免 2 周复盘窗口被材料寻找吃掉。
6. **引用影响面通知**（低）：missed 降级生效后，向引用过该经验的在途项目自动推送提醒，闭环 BR-15 的留痕价值。

## 八、结论

中标复盘是 BidScope 中**设计最完整、约束最严格**的功能域：它用 A/B/C 证据分级回答了"经验是否可信"，用 12 字段 + `scope` 回答了"经验是否适用"，用履约验证 + 等级变更审批回答了"经验是否会过期"，用双人规则和审计回答了"谁改的、能不能改"。机制层面已经自洽；当前的主要短板不在设计，而在**执行侧**——证据可得性、复盘执行率、双 Skill 冲突三个问题决定这套机制能否真正沉淀出知识资产。建议优先完成 Skill 合并与 C 级验证出口两项，其余按优先级滚动。
