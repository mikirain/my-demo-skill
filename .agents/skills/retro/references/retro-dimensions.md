# 十方面复盘框架

> 加载时机：Step 2 核心分析的**第一个**文件。它回答"复盘点什么、每点产出落到 retro.json 哪个字段"。
> 上游依据：`docs/prd/BidScope-PRD-v1.1-中标经验复盘与知识复用.md` §2 十方面差距分析。

## 使用方式

按顺序过 10 个维度，每个维度只做三件事：**问关键问题 → 只认带出处的答案 → 写入指定字段**。
某维度输入材料缺失时，产出该字段并标 `"status": "pending"` + `openItems` 记录待补，**禁止用推断填空**。

| 维度 | 落到 retro.json 的字段 | 主要输入材料 |
| --- | --- | --- |
| 1 客户需求与中标关键因素 | `case` + `winFactors[]` | 招标文件、评分办法、评标反馈 |
| 2 竞品标书与竞争策略 | `winFactors[].competitorGap` + `experiences[category=competitor]` | 竞对标书、中标公示、开标记录 |
| 3 技术方案与产品选型 | `solution` | 投标终版技术卷、参数表 |
| 4 技术偏差与澄清处理 | `solution.deviations[]` + `experiences[category=deviation]` | 偏差表、澄清函往返、客户答复 |
| 5 报价策略与全生命周期成本 | `commercial.priceStructure[]` `commercial.tcoFactors[]` | 报价清单、开标价、TCO 模型 |
| 6 交付能力与本地化服务 | `commercial.delivery` + `experiences[category=commercial]` | 交付计划、服务承诺、本地伙伴协议 |
| 7 认证、合规与安全证明 | `solution.certifications[]` | 证书清单、并网规范、安全标准 |
| 8 商务条款与合同风险 | `commercial.contractRisks[]` + `fulfilment[]` | 合同草案、最终签署版、偏离表 |
| 9 投标组织与跨部门协作 | `process` | 投标计划、评审记录、卡点复盘 |
| 10 中标后履约验证与经验闭环 | `fulfilment[]` + `experiences` 等级变更 | 交付节点、验收记录、客户投诉 |

## 1. 客户需求与中标关键因素

- **目的**：把"赢"拆成评分因素级别的事实，区分强制项（不满足即废标）与评分项（拉开差距）。
- **关键问题**：
  1. 招标文件里哪些是废标项？我们逐项满足的证据是什么？
  2. 评分办法的权重表长什么样？我们哪几项拿到最高分，哪几项失分？
  3. 客户"明文要求"与"实际关注"是否一致？（不一致处往往才是真赢因）
- **产出**：`winFactors[]`，每条必须含 `customerNeed` / `ourResponse` / `competitorGap` / `evidence[]` / `level`。
- **陷阱**：
  - 把"我们做了"写成"客户认可"——`ourResponse` 是事实，客户是否认可必须由 `evidence` 证明。
  - 只看总分不看分项，导致把"总分领先"误当作"每条都赢"。
  - 强制项满足就写 A 级：满足是**入场条件**，不构成赢因；赢因要说明"相对竞对差多少"。

## 2. 竞品标书与竞争策略

- **目的**：把"谁赢在哪"落成事实，把竞对策略沉淀成可复用条目。
- **关键问题**：
  1. 参与方有谁？各家方案的产品路线、关键参数、报价区间（仅限公开或合法渠道信息）。
  2. 我方差异化的三条主张，是否在评分表上真的有分？
  3. 竞对在哪个维度明显强/弱？下次同类项目应主攻哪条？
- **产出**：`winFactors[].competitorGap`（写"竞对 A 效率 94.2%，我方 95.6%，差距 1.4pp，来源 EV-07"）+ `experiences[competitor]`。
- **红线**：禁止推断对手利润率、成本结构、内部决策。竞对报价只记录**开标公开价**并注明来源。
- **陷阱**：把"我们觉得竞对弱"写成结论；用未披露参数（`undisclosed`）比较并宣称优势。

## 3. 技术方案与产品选型

- **目的**：回答"为什么是这套配置"，并识别过度配置（花钱不加分）与不足配置（丢分/风险）。
- **关键问题**：
  1. 硬门槛参数有哪些？我们的实测/认证值 vs 招标要求。
  2. 差异化参数（效率、衰减、可用率、噪声、消防）我们选了哪一档？竞对最好水平多少？
  3. 哪些配置是"加分项上再加钱"？哪些是"客户不关心却写进承诺"？
- **产出**：`solution.hardGateParams[]`（含 `status: meet | deviation | noResponse`）、`solution.differentiators[]`、`solution.configJudgement{overSpec,underSpec}`。
- **陷阱**：不写选定理由只写参数值；把营销口径（循环次数）与实测口径混用。

## 4. 技术偏差与澄清处理

- **目的**：让"这次怎么解释的"变成"下次可以照抄的应答"。
- **关键问题**：
  1. 有几条偏差？是主动偏差（策略性）还是被动偏差（做不到）？
  2. 澄清函怎么问、怎么答？客户是否书面接受？
  3. 这条偏差在下一个项目会不会再出现？可复用的话复用文本是什么？
- **产出**：`solution.deviations[]`（`reason` / `clarification` / `customerAccepted` / `reusable`）+ `experiences[deviation]`。
- **陷阱**：客户口头接受记为 `customerAccepted: true`——口头不算，必须写来源与形式。
- **等级提示**：客户书面澄清明确接受 → 可评 A；只有投标文件自述接受 → 最高 B。

## 5. 报价策略与全生命周期成本

- **目的**：把"价格怎么组"和"为什么客户觉得值"分开记录；不生成报价、不测算对手成本。
- **关键问题**：
  1. 报价结构：储能系统/EPC/运维/备件各占多少？供货范围与竞对差异在哪（含/不含变压器、消防、并网）？
  2. TCO 影响因素：循环寿命、衰减保证、辅助功耗、质保年限、运维费率。
  3. 价格分与 TCO 分各占多少权重？我们靠哪头赢？
- **产出**：`commercial.priceStructure[]`（占比 + 口径说明）、`commercial.tcoFactors[]`；`commercial.noQuoteStatement: true` 表示本次复盘未产出报价建议。
- **红线**：**不产出报价、不推断对手利润率**。价格结论只能是"结构差异"与"权重影响"。
- **陷阱**：把"最低价中标"简单归因于价格，忽略评分权重与技术分补偿。

## 6. 交付能力与本地化服务

- **目的**：把交付承诺变成可核对的时长与依赖清单，防止"投标时敢写、交付时做不到"。
- **关键问题**：
  1. 清关/运输/安装/并网各耗时多少天？哪一段依赖第三方？
  2. 服务承诺（响应时间、备件库、驻场人数）靠什么支撑？自有还是伙伴？
  3. 承诺与历史项目实际偏差有多大？
- **产出**：`commercial.delivery{leadTimeDays, localization, thirdPartyRisks[]}` + `experiences[commercial]`。
- **陷阱**：只写总工期不写分段；把"计划"写成"已具备能力"。

## 7. 认证、合规与安全证明

- **目的**：把"证书覆盖哪些型号、有效期到何时、强制还是加分"记清楚，避免重复踩坑。
- **关键问题**：
  1. 本项目强制要求的认证（并网、消防、运输、安全）分别是什么？
  2. 我方证书覆盖型号与有效期是否精确匹配？缺口如何覆盖（自有/借用/承诺补证）？
  3. 竞对在哪个认证上有优势？
- **产出**：`solution.certifications[]`（`name` / `scope` / `validUntil` / `mandatory` / `gapRisk`）+ `experiences[deviation]` 合规子类。
- **陷阱**：写"已通过认证"而不写覆盖型号与有效期——这是海外项目最常见的失分点。

## 8. 商务条款与合同风险

- **目的**：识别"中标后留下的难兑现义务"，与履约验证联动。
- **关键问题**：
  1. 合同里哪些条款是红旗（无限责任、付款滞后、单方终止、性能罚则）？
  2. 谈判中我们让了什么？让步是否变成硬承诺？
  3. 这些承诺是否已进入 `fulfilment[]` 跟踪？
- **产出**：`commercial.contractRisks[]`（`clause` / `redFlag` / `concession` / `impactOnFulfilment`），并确保每条让步在 `fulfilment[]` 有对应记录。
- **红线**：不做法律意见结论，只做事实摘录 + 风险提示，最终判断交法务/合规。

## 9. 投标组织与跨部门协作

- **目的**：把流程卡点变成流程经验，而不是只复盘技术。
- **关键问题**：
  1. 商务/技术/法务/供应链各在什么时点介入？晚介入造成了什么返工？
  2. 哪些卡点导致了赶工或漏项？（材料缺失、报价审批、澄清回函时限）
  3. 哪一次审核真正拦住了错误？哪些审核是空转？
- **产出**：`process{involvementTimeline[], blockers[], effectiveReviews[]}` + `experiences[awarded]` 流程子类。
- **陷阱**：写成"团队协作良好"的空话——必须写具体时点、具体拦截项。

## 10. 中标后履约验证与经验闭环

- **目的**：把"赢过"和"做得到"分开看，用履约结果反向修正投标期判断。
- **关键问题**：
  1. 复盘时已能观测的承诺有哪些？（交付、效率、响应、质保、备件）
  2. 每条承诺的目标值 / 实际值 / 偏差是什么？状态是 `met / partial / missed / pending`？
  3. 出现 `missed` 时，当初支撑该承诺的经验是否该降级？影响了哪些已引用项目？
- **产出**：`fulfilment[]`；`missed` 触发 `experiences[].pendingChange`（降级）+ `changeHistory` 留痕 + 复核说明 ≥ 6 字。
- **陷阱**：履约数据没到就填 `met`；`missed` 只写"略有延迟"（不足 6 字，脚本拒绝）。

## 三栏归档规则（十方面跑完后的收口动作）

| 三栏 | 判定 | 允许进入 |
| --- | --- | --- |
| 已证实优势（A） | 有评分表/评标反馈/客户书面认可直接指向 | 策略建议、经验库 `verified` 候选 |
| 可能原因（B） | 多份材料共同指向，无评标直接证据 | 参照区，必须附限制说明 |
| 待验证假设（C） | 只有结果无因果，或只有内部判断 | 仅假设区，不进结论载体；须填 `verificationPlan` |

十方面里凡是"只有我们自己这么说"的内容，一律落在 C 栏或 `openItems`，不得升格。
